# KwikPaste 局域网同步协议 v2

本文是 `kwikpaste-core` 里 `sync` 模块的线上约定，改协议时先改这里。实现见同目录的
`protocol.rs`（消息）、`transport.rs`（加密通道）、`discovery.rs`（mDNS）、`service.rs`（握手与会话）、
`engine.rs`（补齐与入库），以及 `db/sync.rs` 与迁移 `0006_sync_seq.sql`（本机序号）。

## 1. 范围

- 设备之间对等，没有主机：每台设备既监听也主动连接，同一对设备只保留一条连接。
- 只同步**本机采集的新记录**：文本（纯文本 / HTML / RTF，以及 URL、邮箱等子类型）与图片。
- 不同步：文件记录、敏感内容、收藏、置顶、分组、备注、删除。从别的设备收到的记录、从备份导入的记录
  不会再转发给其他设备。
- 记录没有跨设备的 id，两边按内容指纹（与本机复制同一套 `content_hash`）去重。
- 1.x 的 v1 协议从未对外开放，v2 与它不兼容（见 §8）。

## 2. 发现（mDNS / DNS-SD）

| 项 | 值 |
| --- | --- |
| 服务类型 | `_kwikpaste._tcp.local.` |
| 实例名 | 设备 id（公钥 BLAKE3 哈希的前 20 个十六进制字符） |
| 主机名 | `kwikpaste-<设备 id>.local.` |
| 端口 | 本机监听端口（默认 41573，被占用时随机） |

TXT 记录（只有这些，不放任何密钥或内容）：

| 键 | 含义 |
| --- | --- |
| `id` | 设备 id |
| `name` | 设备名（设置里填的，留空用系统电脑名） |
| `pf` | 平台：`macos` / `windows` |
| `v` | 支持的最高协议版本（十进制） |
| `vmin` | 支持的最低协议版本；缺省等于 `v`（1.x 只写了 `v=1`） |

- IPv4 与 IPv6 都广播，不广播回环地址。
- 链路本地 IPv6（`fe80::/10`）地址必须带上收到它的网卡编号（scope id）才能连接；拿不到编号的丢掉。
- `v` / `vmin` 读不懂的服务忽略；版本范围与本机没有交集的设备照样列出（`compatible = false`），
  界面提示升级，配对时再报出具体是哪一边旧了。
- mDNS 不通（路由器拦组播、跨网段）时，可以手动按地址配对或连接（§9）。

## 3. 连接与加密

1. TCP 连接。IPv4 与 IPv6 各一个监听，用同一个端口（IPv6 监听设 `IPV6_V6ONLY`）。
2. Noise 握手：`Noise_XX_25519_ChaChaPoly_BLAKE2s`，prologue 固定为 ASCII `KwikPaste LAN sync`
   （**不带版本号**：prologue 不同握手就过不去，版本要在握手之后协商）。双方静态密钥是各自的 X25519 身份密钥。
3. 帧：每条 Noise 消息前加 `u16` 大端长度。握手消息 payload 为空。
4. 握手之后每条应用消息（§4）拆块加密：第一块明文是 4 字节大端 `u32` 总长，之后是内容，
   每块明文不超过 65519 字节（Noise 单条 65535 字节含 16 字节 tag）。读写两个方向各自从 nonce 0 递增。
5. 设备 id = BLAKE3(对方静态公钥) 的前 20 个十六进制字符。连到自己（id 相同）立即断开。

单条应用消息上限：

| 阶段 | 上限 |
| --- | --- |
| 认证完成前（`hello` 到 `welcome` / 配对结束） | 64 KiB |
| 认证完成后（接收方） | 4 + 16 MiB（JSON 头上限）+ 本机申报的附件上限 |
| 发送方的硬上限 | 4 + 16 MiB + 100 MiB（设置里能选的最大图片） |

超过接收方上限的消息直接断开连接，所以发送方必须按对方申报的 `maxAttachmentBytes` 先跳过（§6.4）。

## 4. 应用消息格式

```
u32 大端：JSON 头长度 N（N ≤ 16 MiB）
N 字节：JSON 头（UTF-8）
其余字节：附件（图片的原始 PNG；没有附件时为空）
```

JSON 头是带 `type` 标签的对象，字段名 camelCase。消息类型：

| `type` | 方向 | 字段 | 用途 |
| --- | --- | --- | --- |
| `hello` | 发起方 → 被连接方 | `device`、`intent` | 握手后的第一条消息 |
| `welcome` | 被连接方 → 发起方 | `device`、`protocol` | 接受同步会话，`protocol` 是协商出的版本 |
| `pairChallenge` | 被连接方 → 发起方 | `device`、`protocol`、`spake` | 配对：SPAKE2 第二条消息 |
| `pairConfirm` | 发起方 → 被连接方 | `mac` | 配对：发起方确认值 |
| `pairDone` | 被连接方 → 发起方 | `mac` | 配对：被连接方确认值，配对成功 |
| `reject` | 被连接方 → 发起方 | `reason`、`supported`（可选） | 拒绝，之后关闭连接（§7） |
| `ping` | 双向 | — | 保活 |
| `push` | 双向 | `item`、`live` | 一条记录，图片在附件里 |
| `catchUp` | 双向 | `after`、`epoch`（可选） | 请求补齐 |
| `catchUpPage` | 双向 | `until`、`more`、`epoch` | 一页补齐结束，或实时推送之后的检查点 |
| `unpair` | 双向 | — | 发送方已把接收方移出已配对设备 |

`device`（`DeviceInfo`）：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `name` | string | 设备名 |
| `platform` | `"macos"` / `"windows"` | 平台 |
| `appVersion` | string | 应用版本，只用于显示与日志 |
| `protocol` | `{ "min": u16, "max": u16 }` | 支持的协议版本范围（含两端） |
| `listenPort` | u16 | 本机监听端口，对方据此记下「下次怎么连回来」 |
| `maxAttachmentBytes` | u64 | 本机愿意接收的单条附件上限（§6.4） |

`intent`：`{"kind":"sync"}`（已配对设备之间的同步会话）或 `{"kind":"pair","spake":"<hex>"}`（配对）。

`item`（`WireItem`）：

| 字段 | 含义 |
| --- | --- |
| `kind` | `"text"` / `"image"` |
| `subKind` | 文本子类型：`rtf` / `html` / `url` / `email` / `color` / `path`，或 `null` |
| `content` | 文本的源表示（纯文本、HTML 或 RTF）；图片为空字符串 |
| `searchText` | 富文本的纯文本表示；没有时 `null` |
| `summary` | 摘要；没有时 `null` |
| `width` / `height` | 图片尺寸；文本为 `null` |

接收方把记录还原成剪贴板载荷，再走本机采集同一条流程：自己的采集类型、大小上限、敏感内容规则照样生效，
内容指纹也重新计算。

## 5. 握手

### 5.1 版本协商

1. 发起方在 `hello.device.protocol` 里报出自己的版本范围。
2. 被连接方取两个范围交集里的**最高**版本。没有交集时回 `reject`（`reason = "incompatible"`，
   `supported` = 自己的范围）并关闭连接。
3. 有交集时在 `welcome.protocol` / `pairChallenge.protocol` 里告诉发起方选定的版本；
   发起方确认它在自己的范围内，否则断开。
4. 发起方收到 `incompatible` 时比较范围：对方的最高版本低于自己的最低版本 → 「对方版本过旧，请升级对方」；
   对方的最低版本高于自己的最高版本 → 「本机版本过旧，请升级本机」；对方没带 `supported` → 「版本不兼容」。

当前实现只支持版本 2（`min = max = 2`）。

### 5.2 同步会话（已配对设备）

```
发起方                                 被连接方
  ── Noise XX ──────────────────────────▶
  hello { device, intent: sync } ───────▶  检查版本；检查对方公钥是否与配对时固定的一致
  ◀──────────── welcome { device, protocol }   或 reject { notPaired | incompatible }
  （双方进入会话，§6）
```

按地址手动连接时，发起方在 Noise 握手后先确认对方公钥属于已配对设备，不是就断开（「还没有配对」）。

### 5.3 配对

被连接方显示 6 位配对码，每个配对码最多尝试 5 次（每次收到配对请求就扣一次，中途断开也算），
成功或用完后换新码。

```
发起方（输入配对码）                    被连接方（显示配对码）
  hello { device, intent: pair { spake: SPAKE2 A 消息 } } ──▶  检查版本；扣一次尝试次数
  ◀── pairChallenge { device, protocol, spake: SPAKE2 B 消息 }
  pairConfirm { mac: 发起方确认值 } ──────────────────────────▶  校验
  ◀── pairDone { mac: 被连接方确认值 }                          或 reject { wrongCode }
  （双方记下对方公钥，进入会话，§6）
```

- SPAKE2：Ed25519 群，身份 `kwikpaste-lan-dialer`（发起方，A）/ `kwikpaste-lan-listener`（被连接方，B），
  密码是 6 位数字的 ASCII。
- 确认值：`key = BLAKE3.derive_key("KwikPaste LAN pairing confirmation v1", SPAKE2 共享密钥)`，
  `mac = BLAKE3.keyed(key, 角色标签 ‖ Noise 握手哈希 ‖ 发起方公钥 ‖ 被连接方公钥)`，
  角色标签是 `dialer` / `listener`，hex 编码。发起方先交出自己的确认值，被连接方验证通过才回 `pairDone`。
- 尝试次数用完时回 `reject { pairingUnavailable }`。

## 6. 会话

### 6.1 连接去重与保活

- 同一对设备两边同时连上时，保留设备 id 较小一方发起的那条；发起方相同（旧连接还没发现断开）时新的替换旧的。
- 每 20 秒发一次 `ping`；60 秒没收到任何消息就断开。断开后定期重连（mDNS 地址 + 上次连上的地址），
  失败时退避 5 秒起、最长 120 秒。

### 6.2 本机序号、代次与水位线

- 本机采集（监听剪贴板、手动读取、宿主入库）的记录在入库后分到下一个**本机序号**（`clipboard_items.sync_seq`，
  来自单行计数器 `sync_counter`，只增不减）；再次复制已有内容时重新编号。
  同步收到的、备份导入的记录没有序号，永远不会被补齐给别的设备——这就是记录的来源标记。
- **代次**（`epoch`）是计数器那一行的创建时间。数据库重建（重装、清空数据）后序号从头编，代次跟着变；
  覆盖导入备份时代次也会变。
- **水位线**由接收方按对端分别保存（`peers.json` 的 `watermark` + `epoch`）：已经收齐的对方本机序号。
  不用任何一边的时钟。

### 6.3 补齐

连上后双方各自发一次 `catchUp { after: 水位线, epoch: 水位线所属代次 }`（第一次补齐没有 `epoch`）。
收到请求的一方：

1. `epoch` 与自己当前代次不同（或没有）时，把 `after` 当作 0，从头发。
2. 候选记录：有本机序号、序号大于 `after`、最近 7 天内用过、不是敏感内容也不是文件；
   总量只取最新的 500 条（更早的跳过）。
3. 按序号从小到大取一页（最多 50 条），逐条发 `push { live: false }`，跳过本机设置不同步的类型、
   超过 `min(本机图片上限, 对方 maxAttachmentBytes)` 的图片、超过 JSON 头上限的文本。
4. 最后发 `catchUpPage { until, more, epoch }`：`more` 为真时 `until` 是这一页最后一条的序号；
   否则 `until = max(本机计数器, 这一页最后一条)`。计数器在取页之前读，取页期间新复制的记录留到下一次。

接收方按顺序处理：`push` 逐条入库，收到 `catchUpPage` 时说明前面的记录都已入库，把水位线推进到 `until`
（同一代次只往前走，代次变了整个替换）；`more` 为真就接着发 `catchUp { after: until, epoch }`。

**检查点**：最后一页（`more = false`）发出后，发送方对这条连接记下「对方已收齐到 `until`」。之后本机每次采集
（每个序号恰好对应一次采集）要么实时推送、要么按规则不需要推送（敏感、文件、本机不同步的类型、超过附件上限、刚同步过的回声），
从 `until` 起连续处理过的序号随即以 `catchUpPage { until: 新值, more: false, epoch }` 发给对方，
接收方照常推进水位线。这样实时收到的记录重连后不会再补发一遍。某条推送因为发送队列满被丢掉、或读图失败时，
这条连接不再发检查点，重连后从上一个检查点补齐。

### 6.4 记录与附件

- `push { live: true }`：对方刚刚复制的记录。接收方入库（已有相同内容时按复制已有内容处理），
  设置允许时写入系统剪贴板；最近一次同步过的同一内容 60 秒内视为回声，不再写剪贴板也不再发回去。
  水位线只由 `catchUpPage`（补齐的页尾或检查点）推进；对方离线或发送队列满时丢掉的记录，下次补齐时会补上。
- `push { live: false }`：补齐的历史。只在本机还没有相同内容时插入，已有的不动（不刷新时间、
  不增加使用次数、不写剪贴板）。
- 附件上限跟随各自设置里的「图片大小上限」（1–100 MB），不收图片时申报 0。发送方对每台设备按它申报的
  `maxAttachmentBytes` 分别跳过放不下的图片；接收方再按自己当前的设置检查一次。上限在连接建立时交换，
  会话期间改设置，下次连接生效（接收方自己的检查立即生效）。

### 6.5 取消配对

一方取消配对时先从本机移除，对方在线就发 `unpair` 再断开；收到 `unpair` 的一方也移除对方。
对方离线时，下次它连过来会收到 `reject { notPaired }`，也随之移除。

## 7. 错误码（`reject.reason`）

| 值 | 含义 | 发起方提示 |
| --- | --- | --- |
| `notPaired` | 同步会话的发起方不是已配对设备（或公钥变了） | 还没有配对 / 对方已取消配对 |
| `pairingUnavailable` | 配对码尝试次数已用完 | 对方的配对码已失效，请刷新 |
| `wrongCode` | 配对码不对（确认值不符或 SPAKE2 失败） | 配对码不正确 |
| `incompatible` | 没有共同的协议版本（带 `supported`），或请求了不认识的 `intent` | 对方版本过旧 / 本机版本过旧 / 版本不兼容 |
| 其他值 | 更新的版本才有的原因，按 `unknown` 处理 | 连不上这台设备 |

`reject` 之后被连接方关闭连接。连接在握手阶段失败（Noise 握手不过、超时）没有错误码，发起方提示连不上。

## 8. 兼容规则

1. **不认识的消息类型跳过**，不断开连接；JSON 头读不懂（字段取值是新版本才有的枚举值等）也按不认识的消息跳过。
   只有长度字段对不上、超过上限、解密失败才断开。
2. **不认识的字段忽略**。新增字段必须带默认值（可选），老版本不发时新版本也能工作。
3. 枚举里不认识的取值：`reject.reason` 按 `unknown`，`intent.kind` 按 `unknown`（回 `incompatible`），
   `item.kind` / `subKind` 不认识时整条 `push` 跳过。
4. `hello`、`welcome`、`reject` 的形状在所有版本里保持不变（字段只增不删），版本不兼容的设备之间也能读懂
   拒绝原因。Noise 参数与 prologue 永远不变。
5. 只加消息类型或可选字段（例如以后同步收藏、备注、删除）**不需要**升协议版本：老版本跳过新消息即可。
   改变已有消息的含义、必填字段或加密方式时才升版本，新版本在一段时间内同时支持新旧版本（`min < max`）。
6. 1.x 的 v1 协议（prologue 带版本号、按对方时钟补齐）与 v2 在 Noise 握手阶段就不通；1.x 从未对外开放同步，
   不做兼容。mDNS 上看到 `v=1` 的设备显示为版本不兼容。

## 9. 地址

- 手动配对 / 连接支持：`192.168.1.8`、`192.168.1.8:41573`、`::1`、`[2001:db8::5]:41573`、
  带网卡的链路本地地址 `fe80::1%12`、`[fe80::1%12]:41573`、`fe80::1%en0`（网卡写编号或名字都行），
  以及主机名（可带端口）。缺端口时用 41573。
- 已配对设备记下最近一次连上的 `地址:对方监听端口`（IPv6 保留 scope id），mDNS 不通时用它重连。
- 本机地址列表：IPv4 在前（默认路由所在网卡第一），然后全局 IPv6、链路本地 IPv6（带 `%scope`，
  Windows 写网卡编号、macOS 写网卡名）；虚拟网卡（Hyper-V、WSL、VMware、VirtualBox）的地址只在没有别的地址时列出。
- 拨号顺序：与本机同一 /24 网段的 IPv4、其他 IPv4、全局 IPv6、链路本地 IPv6。

## 10. 测试约定

自动测试只在本机回环地址（`127.0.0.1` 与 `::1`）上监听随机端口、不广播 mDNS（`LanSyncNetwork::loopback()`），
剪贴板一律用内存剪贴板。两台真机之间的发现、IPv6 链路本地连接、防火墙与跨平台测试另行安排。
